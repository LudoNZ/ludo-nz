## Explanation

**The case:** *"At handover, a project manager needs a PDF QA report for a whole project: every lot, every checklist, results, photos and sign-offs. It can be hundreds of pages. Design report generation."*

**Why not do it in the request?** A large report takes far longer than an HTTP request should, and longer than API Gateway will wait. Generating it in the API means timeouts, retries that start the work again, and an API tied up doing heavy work. So: **accept the request quickly, do the work in the background, notify when done.**

**The shape:**

1. `POST /projects/:id/reports` with options (lots, date range, include photos?). The API validates permissions, inserts a `report_jobs` row (`status = 'queued'`, `requested_by`, options, `idempotency_key`), sends a message `{ jobId }` to an SQS queue, and returns **202 Accepted** with the job id. Ideally the row insert and the message are atomic. A simple approach is a transactional outbox (insert an outbox row in the same transaction, and a relay sends it), or let a worker poll the jobs table.
2. A **worker Lambda** (or a container task for very long jobs, since Lambda has a maximum duration of 15 minutes) consumes the message: it marks the job `running`, queries the data (the big SQL from the SQL module: latest responses, sign-offs, photos), renders the PDF (streaming, page by page, to keep memory bounded), uploads it to S3, and marks the job `done` with the S3 key, or `failed` with an error.
3. The client **polls** `GET /reports/:jobId` every few seconds (simple and robust), or gets a push notification or email with a link. Downloads use a short-lived presigned GET.

**Failure modes and the answers interviewers want:**

- **Duplicate delivery** (SQS is at-least-once): the worker claims the job with a conditional update (`UPDATE report_jobs SET status = 'running' … WHERE id = $1 AND status = 'queued'`). If 0 rows, someone else has it, so skip. Output keys are deterministic per job, so a rerun overwrites rather than duplicates.
- **Worker crashes mid-job**: the message becomes visible again after the visibility timeout (set it longer than the job's maximum time). A job stuck in `running` with an old `started_at` is reclaimable, using a heartbeat or lease column.
- **Poison job** (bad data makes rendering throw every time): retries up to `maxReceiveCount`, then the DLQ, with the job marked `failed` and the user told. An alarm on the DLQ.
- **Data changing during generation**: read in one transaction with `REPEATABLE READ` for a consistent snapshot, or stamp the report "as at <time>" and only include records up to that time. For a QA handover, "as at" matters legally. Ask.
- **Huge projects**: memory and time limits, so paginate queries, stream the PDF, fetch photos in parallel with a concurrency limit, or split into per-lot PDFs and zip them. Move to Fargate or a container if jobs exceed Lambda's limits.
- **Noisy neighbour**: one company requesting 50 reports shouldn't block everyone. Per-tenant concurrency limits, or a separate queue for large jobs.
- **Cost and retention**: S3 lifecycle rules expire generated reports after N days (they can be regenerated), *unless* a report is the formal handover record, in which case it's kept with the audit trail.

**Alternative: Postgres as the queue.** For modest volumes, a `report_jobs` table polled with `SELECT … FOR UPDATE SKIP LOCKED` is a legitimate queue: transactional with your data, no extra service, easy to inspect. SQS wins on scale, built-in retries and DLQ, and decoupling. Mentioning both, with when you'd pick each, is a strong answer.

## Worked example

The jobs table and the `SKIP LOCKED` claim pattern. Each worker takes the oldest queued job no other worker has locked, atomically:

```sql
CREATE TABLE report_jobs (
  id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  project_id      bigint NOT NULL REFERENCES projects (id),
  requested_by    bigint NOT NULL REFERENCES users (id),
  status          text NOT NULL DEFAULT 'queued' CHECK (status IN ('queued', 'running', 'done', 'failed')),
  attempts        int NOT NULL DEFAULT 0,
  idempotency_key uuid UNIQUE,
  output_key      text,
  error           text,
  created_at      timestamptz NOT NULL DEFAULT now(),
  started_at      timestamptz,
  finished_at     timestamptz
);
CREATE INDEX report_jobs_queued_idx ON report_jobs (created_at) WHERE status = 'queued';

INSERT INTO report_jobs (project_id, requested_by, idempotency_key)
VALUES (1, 2, 'aaaaaaaa-0000-4000-8000-000000000001'),
       (2, 2, 'aaaaaaaa-0000-4000-8000-000000000002');

-- a worker claims the next job
UPDATE report_jobs
SET status = 'running', started_at = now(), attempts = attempts + 1
WHERE id = (
  SELECT id FROM report_jobs
  WHERE status = 'queued'
  ORDER BY created_at, id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
RETURNING id, project_id, attempts;
```

`FOR UPDATE SKIP LOCKED` makes concurrent workers pass over rows another transaction has locked, rather than waiting, so ten workers claim ten different jobs with no double-processing. The partial index keeps "find the next queued job" fast however many finished jobs pile up.

## Exercises

### Finish or fail a job [1]

Write the two statements a worker runs at the end: marking a job done with its output key, and marking it failed with an error. Both must only apply if the job is still `running` (a reclaimed job must not be overwritten by a slow, stale worker).

#### Solution

```sql
CREATE TABLE report_jobs (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, project_id bigint NOT NULL REFERENCES projects (id),
  requested_by bigint NOT NULL REFERENCES users (id), status text NOT NULL DEFAULT 'queued',
  attempts int NOT NULL DEFAULT 0, output_key text, error text,
  created_at timestamptz NOT NULL DEFAULT now(), started_at timestamptz, finished_at timestamptz
);
INSERT INTO report_jobs (project_id, requested_by, status, started_at, attempts) VALUES (1, 2, 'running', now(), 1);

UPDATE report_jobs
SET status = 'done', output_key = 'companies/1/reports/1.pdf', finished_at = now()
WHERE id = 1 AND status = 'running' AND attempts = 1
RETURNING id, status;

UPDATE report_jobs
SET status = 'failed', error = 'Photo 123 could not be read', finished_at = now()
WHERE id = 1 AND status = 'running' AND attempts = 1
RETURNING id, status;
```

The first returns the row and the second returns nothing, because the job is already done. Including `attempts` (which attempt *this* worker claimed) in the `WHERE` acts as a fencing token: a stale worker from attempt 1 can't overwrite the result of attempt 2. It's the same conditional-update idea as signing off.

### Reclaim stuck jobs [2]

Write the query a scheduled job runs to put `running` jobs back to `queued` if they started more than 20 minutes ago, and to fail them permanently after 3 attempts.

#### Solution

```sql
CREATE TABLE report_jobs (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, project_id bigint NOT NULL REFERENCES projects (id),
  requested_by bigint NOT NULL REFERENCES users (id), status text NOT NULL DEFAULT 'queued',
  attempts int NOT NULL DEFAULT 0, output_key text, error text,
  created_at timestamptz NOT NULL DEFAULT now(), started_at timestamptz, finished_at timestamptz
);
INSERT INTO report_jobs (project_id, requested_by, status, started_at, attempts) VALUES
  (1, 2, 'running', now() - interval '45 minutes', 1),
  (2, 2, 'running', now() - interval '45 minutes', 3),
  (3, 2, 'running', now() - interval '5 minutes', 1);

UPDATE report_jobs
SET status     = CASE WHEN attempts >= 3 THEN 'failed' ELSE 'queued' END,
    error      = CASE WHEN attempts >= 3 THEN 'Timed out after 3 attempts' ELSE error END,
    started_at = CASE WHEN attempts >= 3 THEN started_at ELSE NULL END
WHERE status = 'running'
  AND started_at < now() - interval '20 minutes'
RETURNING id, status, attempts;
```

Job 1 is requeued, job 2 fails permanently, and job 3 (still within its window) is untouched. The 20 minutes must exceed the longest legitimate job. A heartbeat column updated by the worker every minute is more precise than a fixed timeout. The SQS equivalent is the visibility timeout plus `maxReceiveCount` and a DLQ.

### Polling vs push [1]

The PM requests a report and waits. Compare polling `GET /reports/:id` with pushing a notification. Which would you build first?

#### Solution

Polling: simple, stateless, works through proxies and on flaky mobile networks, and is easy to test. It costs a few cheap requests (poll every 2–5 s with backoff, and stop after it's done). Push (WebSocket, server-sent events or mobile push): instant and no wasted requests, but needs connection management, reconnection, and infrastructure (API Gateway WebSockets, or a service). Email or in-app notification: right for long jobs where the user leaves. Build first: polling while the page is open, plus an email or in-app notification for reports taking more than a minute. Add live push only if users actually need instant updates. It's the "simplest thing that meets the requirement" answer, with a clear upgrade path.

## Say it aloud

"Design generation of a large PDF QA report for a whole project."

#### Model answer

It's too slow for a request, so I'd make it a background job. The API validates access, inserts a report job row as queued with an idempotency key so double clicks don't create two, puts the job id on an SQS queue, and returns 202 with the job id. A worker picks it up and claims the job with a conditional update from queued to running, so a duplicate delivery is skipped. It reads the data in a consistent snapshot and stamps the report "as at" a time, because for handover that matters. It streams the PDF to S3 to keep memory bounded, and marks the job done with the key. If it crashes, the message comes back after the visibility timeout. Stuck running jobs get reclaimed, and after a few attempts the message goes to a dead-letter queue with an alarm, and the job is marked failed so the user knows. The client polls the job status and downloads with a presigned URL, with an email for long jobs. For modest volumes I'd consider a jobs table with SELECT FOR UPDATE SKIP LOCKED instead of SQS. And for very large projects I'd move the worker to a container or split the report per lot to stay inside Lambda's limits.
